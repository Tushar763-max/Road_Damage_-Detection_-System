1. Purpose

This volume collects the architecture and UML-style diagrams for RoadScan AI. The diagrams match the running design: a React client, a Flask and YOLOv8 server, and a SQLite file. They are implementation diagrams for the viva, drawn from the modules that exist in the repository.

2. Architectural style

The style is a three-tier client-server. The presentation tier is a single-page application. The application tier is stateless apart from the loaded model and the SQLite file on disk. There is no separate message queue. Video work happens inside the request, which is acceptable only because stride and a frame cap bound the work.

2.1 Why the model stays behind Flask

Loading YOLOv8 in the browser would publish the weight file and would be heavy on a student laptop’s GPU drivers. Keeping inference in Python matches the Ultralytics API and lets OpenCV and FFmpeg share one pipeline.

3. Use case diagram

The human actor is a surveyor who may also file a citizen-style complaint. The model is shown as a supporting actor because detection use cases cannot complete without it. Login is local. Health is a separate use case so the examiner can prove the model is loaded before trusting a screenshot.

4. Sequence diagram

The video sequence inserts a loop between steps 3 and 4: read a frame, skip according to stride, predict, keep the annotated frame, stop at 90 inferences or end of file, then encode. The live-camera sequence omits the database insert.

6. Class diagram

The browser does not use a classical inheritance hierarchy for domain objects. The diagram shows the modules and the two records they pass. Detection is the box. HistoryRecord is the stored job. The Flask module owns the functions severity, compute_risk, save, and the route handlers.

7. State diagram

The implementation accepts any of the four statuses from any of the others. A stricter state machine that forbids moving from repaired back to reported would be a future rule. The diagram shows the intended operational order.

11. Entity-relationship diagram

There is no foreign key between complaints and history. A complaint photo that is analysed does not also insert a history row in the current code. Maps union the two tables at read time. That is why source_table is added in the tracker response and is not a stored column.
