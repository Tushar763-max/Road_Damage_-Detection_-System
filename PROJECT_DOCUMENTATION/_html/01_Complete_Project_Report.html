Abstract

Indian roads accumulate potholes, longitudinal cracks, transverse cracks, and alligator cracking. Manual inspection is slow and the record of a defect often stays on paper or in a photograph without a consistent location, severity tag, or repair trail. RoadScan AI is a web system that accepts a road image, a short video, a live camera frame, or a citizen complaint, runs a YOLOv8 detector, draws bounding boxes, estimates severity from the box area and class, computes a 0–100 risk score, and stores the record in SQLite. A React dashboard then shows history, charts, a map of stored coordinates, a damage heatmap, a repair workflow, and a printable inspection report.

The frontend is React 19 with TypeScript, Vite, and Tailwind CSS. The backend is Flask with Ultralytics, OpenCV, and imageio-ffmpeg. The default weight file is backend/YOLOv8_Small_RDD.pt. If that file is absent, the server loads backend/best.pt. An environment variable MODEL_PATH overrides both. Login is a local browser session used to protect the dashboard during demonstration. It is not a server-side user directory. The project is intended for academic demonstration and municipal-style workflow practice, not as a production traffic-safety system.

Chapter 1 — Introduction

1.1 Background

Road agencies and municipal wards need a repeatable way to notice surface damage. A photograph from a phone already contains most of the visual evidence, but a folder of photographs does not answer which frame contained a pothole, how confident the detector was, whether the defect is small or large in the frame, or whether a crew has been assigned. RoadScan AI keeps that evidence attached to a detection record.

1.2 Problem statement

Design and implement a student-deployable system that detects common road-damage classes from images and videos, explains each detection with class name, confidence, and a severity band, retains history, and supports a simple reported–assigned–in progress–repaired trail. The system must show a clear error when the model service is offline instead of inventing detections.

1.3 Objectives

  • Detect road damage with a YOLOv8 model and return bounding boxes.
  • Provide separate workflows for still images, video files, and live camera frames.
  • Map dataset class codes such as D00, D10, D20, and D40 to readable names when those codes are present.
  • Estimate severity from box area and class, and compute a capped risk score.
  • Store detections and citizen complaints with optional latitude, longitude, and place name.
  • Show dashboard counts, analytics charts, a coordinate tracker, and a heatmap built only from stored coordinates.
  • Allow a repair status update with an audit note.
  • Generate a browser inspection report that can be printed.

1.4 Scope

In scope: a single-workstation demonstration, one SQLite database, one loaded weight file, browser login for the user interface, and English labels. Out of scope: official IRC or MoRTH pavement ratings, multi-tenant production security, automatic work-order dispatch to a contractor, and measured depth of a pothole in millimetres. Depth cannot be recovered from a single ordinary photograph.

Chapter 2 — Literature review and existing practice

2.1 Manual inspection

A ward engineer walking or driving a stretch can miss defects, and two inspectors will not mark the same crack in the same way. Photographs help, but without a structured record the photograph is detached from the repair decision. The proposed system does not replace the engineer. It gives the engineer a first-pass visual list.

2.2 Object detection

Modern one-stage detectors such as the YOLO family predict boxes and classes in a single forward pass. YOLOv8, distributed through the Ultralytics library, is a practical choice for an MCA project because the same Python API trains and runs inference, and a .pt weight file can be dropped beside the Flask application. The server calls model.predict with imgsz 640, which matches the usual YOLO training resolution and helps smaller damage remain visible.

2.3 Road-damage datasets

Published smartphone datasets label damage with codes such as D00 (longitudinal crack), D10 (transverse crack), D20 (alligator crack), and D40 (pothole). Later sets also discuss markings such as blurred white lines and crosswalks. RoadScan AI does not retrain a model inside the web request. It loads a prepared weight file and translates known codes through CLASS_ALIASES. The class list actually available is whatever the loaded file exposes, and the health endpoint returns that list.

2.4 Limitations of typical student demos

  • Desktop-only scripts that print boxes in a console and keep no history.
  • Interfaces that display sample detections when the model is down, which hides failure during a viva.
  • No distinction between a crack and a pothole when assigning urgency.
  • No place to record that a repair crew has started work.
  • Video processing that attempts every frame and stalls a CPU laptop.

2.5 What this project adds

RoadScan AI separates the browser from the model, refuses to fabricate detections when Flask is offline, stores each successful image or video analysis, skips frames during video inference with a hard cap, encodes a browser-playable H.264 preview, and adds complaint, map, heatmap, risk, and repair screens on top of detection.

Chapter 3 — System analysis and requirements

3.1 Existing system

The baseline considered here is a manual process: capture photos in a phone gallery, describe the site in a message or register, and prioritise by memory. There is no common confidence value and no single map of open defects.

3.2 Proposed system

A React single-page application talks to a Flask API. Flask loads YOLOv8 once at startup, reads uploads with OpenCV, writes annotated media, and inserts SQLite rows. The browser polls GET /api/health and surfaces Model Online only when the process responds and a weight file is loaded.

3.6 Constraints

  • One Flask process holds the model. A second process started by a reloader would load the weights twice, so use_reloader is disabled.
  • SQLite allows one writer at a time. That matches a demo and is not a city-scale database.
  • Class names depend on the weight file. Documentation must not claim a measured mAP that this repository does not record.
  • best.pt is only a fallback. Project notes record that a custom best.pt produced about one percent confidence in local checks, so the preferred file is YOLOv8_Small_RDD.pt.

5.2 Startup

On import, app.py creates uploads and outputs, chooses the weight path, and constructs YOLO if the file exists. Otherwise model remains None and detection routes return 503 with the message that weights must sit next to app.py. The development server binds 0.0.0.0 on PORT (default 5000) with the reloader off. FLASK_DEBUG can enable the Flask debugger without the reloader.

5.3 Class names

pretty_class maps D00 to Longitudinal Crack, D10 to Transverse Crack, D20 to Alligator Crack, D40 to Pothole, D43 to White Line Blur, D44 to Cross Walk Blur, and the same names written in snake case. Unknown names are shown unchanged. Each detection also keeps raw_class so a viva can show the code the model actually emitted.

5.4 Severity rule

Let the box be (x1, y1, x2, y2) on a frame of width w and height h. The area percentage is (x2-x1)*(y2-y1)*100/(w*h). The base band is high when the percentage is at least 8, medium when it is at least 2, and low otherwise. If the class name contains “crack” and the band would be high, it is reduced to medium, because a long crack can cover area without being a single collapse. If the class is a pothole or the raw code is D40, the band is high at 3 percent or more and medium at 1 percent or more. The record severity is the worst box: high over medium over low.

State this rule in the viva. It is a visual estimate for sorting a list, not a pavement-management index.

5.5 Risk score

An empty detection list scores 0 and category low. Otherwise each box adds a weight times (0.4 + confidence), where confidence is capped at 1. Weights are 12 for low, 24 for medium, and 38 for high. Four or more boxes add 8. The total is rounded and clamped to 0–100. Category is high at 70 or above, medium at 40 or above, and low below 40.

5.6 Image route

POST /api/detect/image requires a file field. Confidence defaults to 0.15 when the form omits it. The React client sends 0.25 for image and video pages unless the user moves the control, and 0.15 for live frames. The file is saved under uploads using a UUID. OpenCV reads it. Failure returns 400. Success draws boxes with Ultralytics plot(), writes outputs/<id>.jpg, returns a data URL, and inserts history.

5.7 Video route

Stride is 5 when the frame count is above 600, 4 above 240, 3 above 120, and 2 otherwise. The loop stops after 90 inferred frames. Each inferred frame is resized to a maximum width of 640 with even width and height. Detections carry a timestamp equal to frame index divided by source frames per second. The preview image is the annotated frame that contained the most boxes. Encoding uses the ffmpeg binary from imageio-ffmpeg with libx264, yuv420p, preset veryfast, CRF 28, and faststart. If ffmpeg is missing, OpenCV mp4v is a fallback and may not play in the browser, though the file can still be downloaded. Encoding failure returns 500.

5.8 Location handling

read_geo parses latitude and longitude from the form. A missing value, a non-number, or a value outside [-90, 90] or [-180, 180] causes coordinates to be stored as null. A place name can still be stored. The heatmap groups remaining points by latitude and longitude rounded to two decimal places. A bucket is a high zone when it has two high-severity or high-risk records, or four records of any kind. Two records make a medium zone. One record is a low zone.

5.9 Complaints and repairs

A complaint requires a description of at least eight characters and a location name. An optional photo is detected when the model is loaded. Without a model, the original image is still stored. Repair updates accept a JSON body with status and an optional note. The kind path segment selects the complaints table or the history table. Any other status returns 400.

5.10 Frontend behaviour that matters in a viva

  • checkHealth aborts after four seconds and tells the user to start Flask.
  • History rows returned by the API are tagged source model and status completed in the client.
  • absoluteMediaUrl prefixes /outputs paths with the API origin.
  • Dashboard stats from the server are file count, sum of detection totals, and the number of high-severity files. The client currently maps the file count into totalImages and sets totalVideos to 0. That mapping is a known limitation and is recorded in the audit.
  • Logout removes only the localStorage session.

Chapter 6 — Testing summary

A separate Software Testing Report lists the test design. This chapter records the strategy. Tests are specified from the source so an examiner can reproduce them. This report does not invent a pass percentage from a run that was not captured. During the viva, health, one image, one short video, one complaint, and one status change should be executed and the observed result written on the test log.

  • API negative tests: missing file, unreadable image, missing model, bad repair status, short complaint text, unknown history id.
  • API positive tests: health, image, video, frame, history list and delete, tracker, heatmap, complaint, repair.
  • Rule tests: severity boundaries at 1, 2, 3, and 8 percent, crack downgrade, empty risk, four-box bonus, score cap.
  • UI tests: password shorter than six characters, protected route, offline banner, model badge when health succeeds.
  • Non-functional checks: video stride selection and the 90-frame cap, even output dimensions, no invented GPS.

Chapter 7 — Results and discussion

7.1 What the demonstration shows

When the weight file loads, /api/health returns model_loaded true and the class list. An image response contains pixel width and height, a detection array, an annotated image, the worst severity, the risk score and category, the repair status reported, and any coordinates the user actually supplied. A video response adds frames processed, stride, duration, and a note that short clips of about 5 to 15 seconds suit a demonstration. A live frame returns saved false.

7.2 What is deliberately not claimed

The repository does not contain a frozen precision, recall, or mAP table for the weight file. Comparing best.pt with YOLOv8_Small_RDD.pt is supported by backend/compare_models.py, and that comparison must be quoted from an actual console log rather than from this narrative. A low-confidence weight should be replaced; the server already prefers YOLOv8_Small_RDD.pt for that reason.

7.3 Discussion

Bounding-box area is a proxy. A close camera makes a small pothole look large. A distant camera does the opposite. The severity rule is still useful because it is deterministic and can be explained. Frame skipping makes video interactive on a CPU and can miss a defect that appears for only one or two frames. The cap of 90 inferences bounds waiting time. Citizen complaints without a photo have no boxes and therefore a low risk until a photo is analysed.

7.4 Sample interpretation

Suppose one pothole box covers 4 percent of the frame with confidence 0.62. The pothole rule sets severity high because 4 is at least 3. The risk contribution is 38 * (0.4 + 0.62) = 38.76, which rounds to 39 and category low, because a single box does not reach 40. A second medium box can push the same site into the medium band. This example is arithmetic from the formula, not a measured field case.

Chapter 8 — Conclusion and future scope

8.1 Conclusion

The project meets its academic objective. A surveyor can upload media, see YOLO boxes with confidence and a stated severity rule, keep a history, place real coordinates on a map, accept a citizen complaint, and move a record along a repair trail. The system fails visibly when the model is absent. That honesty is part of the design.

8.2 Limitations

  • Browser login is not authentication against the API. Any client that can reach port 5000 can call the routes.
  • CORS is open for local development.
  • Output files are served with a video/mp4 content type even when the file is a JPEG.
  • Dashboard stat mapping does not split image and video counts.
  • There is no measured depth, area in square metres, or official defect code for a work order.
  • SQLite and a single process will not serve a city concurrently.

8.3 Future scope

  • Server accounts with hashed passwords and per-user history.
  • A measured evaluation sheet: precision, recall, and mAP on a held-out Indian road set, stored in the repository.
  • Camera calibration or a known mounting height so box size can be converted toward an approximate ground area.
  • PostgreSQL, object storage, and a queue for video jobs.
  • A mobile capture client that always sends GPS.
  • Retraining when new ward photographs are labelled.
  • Role separation so a citizen cannot change a repair status.
